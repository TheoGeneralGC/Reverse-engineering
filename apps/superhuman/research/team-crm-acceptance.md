# Team/CRM candidate acceptance scenarios

These are proposed tests, not executed bindings or verified behavior. Retained evidence supports only the prior Create Team form end state. No mutation scenario below is armed or run by this packet. Original comparison should use the same build/account/context when available; changes in build or entitlement must be recorded. Synthetic implementation tests cannot establish vendor parity.

## SH013: collaboration

| ID | Controlled case | Required evidence / result |
| --- | --- | --- |
| TEAM-01 | In a known empty-composer account, observe existing Team entry/role/disabled state and open only an already reviewed local form. Close without editing. | Record visible controls, exact account-scoped capability reason and no setting/invite/share write. The prior invitation-form evidence is partial support, not a new test result. Do not infer every singleton account gets that state. |
| TEAM-02 | In two authorized disposable identities, share one recipient-free standalone synthetic draft with the explicitly selected peer. | Capture exact author/draft/participant identity, scope warning, one accepted share and peer visibility. No mail Send. Sharing may notify the peer; obtain the specific action authorization before the original test. Unknown response must be recovered without repeated share/invite dispatch. |
| TEAM-03 | Author edits To/Cc/Bcc, rich body and attachment on the owned shared draft while peer observes. | Peer content converges to the same draft; only author receives edit controls according to feature-specific guidance. Measure actual update cadence and preserve both local editor histories. No inferred simultaneous multi-author editing. |
| TEAM-04 | On a preexisting controlled synthetic conversation, share an owned reply draft. | Peer can inspect the exact intended history/subthreads; record what is visible before/after and whether future-message sharing is enabled. Never use real mailbox context to test disclosure. Do not create a new email merely to seed this test. |
| TEAM-05 | Author stops standalone draft sharing, then separately stops reply-draft sharing. | Compare confirmation, draft/comment/thread access and future-sharing scope. Test owned links in a second identity/session; no guest/public access assumption. Preserve unavailable versus forbidden versus stale cache. |
| TEAM-06 | Post one controlled comment, with no mention first; separately test an explicitly approved peer mention. | Comment is distinct from outgoing email and attributed to exact author/time. Mention audience expansion and external notifications are explicit. Delete only that owned comment and observe selection/peer update; do not invent an Edit action if absent. |
| TEAM-07 | Use one controlled shared-thread link as Publisher, participant, permitted guest and unrelated test identity. | Verify identity enforcement, author-only edit, guest comment/reply/forward boundaries and stop/re-share behavior. Link copy itself is not proof of unauthenticated access. Do not publish the link or its opaque token. |
| TEAM-08 | Remove the approved participant from email recipient fields on the owned fixture. | Verify the documented sharing warning and whether sharing remains. Do not treat recipient deletion as authorization revocation. Account switch and stale background results must not expose previous-account draft/comments. |
| TEAM-09 | Exercise offline/unknown share or comment acknowledgement in a synthetic isolated server fixture. | Keyed receipt recovery is read-only; stale account/draft/version ACKs do not replace new edits or create a new invitation/comment. This is a reconstruction safety requirement, not a recovered vendor wire protocol. |
| TEAM-10 | With an existing authorized role fixture, inspect Admin versus Member versus conversation Publisher. | Team management permissions and conversation access remain separate. Team create/join/member/role/billing changes and activity export are outside current inspection and need explicit action scope before comparison. |

## SH019: CRM and sales views

| ID | Controlled case | Required evidence / result |
| --- | --- | --- |
| CRM-01 | Compare disconnected, connected/read-only and Mail-plan-unavailable states for one selected provider. | Exact provider/tenant/account binding, reason, settings entry and absence of fake records. No automatic OAuth connection, upgrade/request or hidden write when the pane opens. Capture actual consent/scopes only during an authorized connection flow. |
| CRM-02 | Hover/select a contact whose synthetic email matches a controlled provider record, then a missing record. | Right pane displays matching provider objects and allowed fields, with exact ownership and nullable/denied/missing distinctions. Account/contact A→B→A and slow old responses must preserve the current pane. |
| CRM-03 | Open basic/object settings; inspect available fields and close unchanged. | Observe object visibility, order, search, field labels/types and loading/offline errors. Confirm whether actual handlers save immediately or stage; no universal Save assumption. Settings metadata reads are distinct from writes. |
| CRM-04 | In a disposable Salesforce/HubSpot workspace, explicitly update one supported field. | Bind provider tenant, object type/ID, prior version and exact changed field. Provider denial/conflict retains authored input; unknown POST requires scoped read-only recovery, not automatic recreation/retry. Verify authoritative provider readback. |
| CRM-05 | Explicitly create one fictional contact where the provider/role allows it. | Provider schema drives required/createable/reference/picklist fields. One actual record, correct associations and no duplicate after a lost ACK. Cleanup only the named fixture under the same scoped authorization. Pipedrive creation remains unimplemented/unmeasured until demonstrated. |
| CRM-06 | Test permission-restricted objects, revoked authentication and missing scopes. | Field/object visibility and editability follow actual provider authorization. Do not equate a client cached flag with server access. Inspect handler side effects before dismissing error dialogs that might sign out or reconnect. |
| CRM-07 | Inspect a HubSpot contact with Sequences available, without selecting a sequence. | Record provider entitlement, accessible choices and immediate-enrollment warning. Enrollment can trigger external emails/automation and is excluded until separately scoped to a non-delivering controlled fixture or explicitly approved test recipient. |
| CRM-08 | Compare Pipedrive existing fields and an Edit command in an authorized connected read-only test context. | Resolve conflicting official instructions by visible controls and actual capability. No cosmetic edit/create feature or inferred support from another CRM. |
| CRM-09 | Inspect outgoing Auto-Bcc configuration without saving/sending. | Keep CRM object integration, email logging and read tracking distinct. Do not add a Bcc or send merely to test the CRM pane. Actual logging needs its own controlled delivery authorization. |
| CRM-10 | Compare supported desktop/web and mobile surfaces only where access exists. | Record device/version differences. Current task has no mobile observation and cannot generalize desktop declarations. |
| CRM-11 | With a preexisting authorized analytics role/data fixture, inspect Team Activity/sales metrics. | Record metric definitions, population, freshness, thresholds, export permissions and provenance. Distinguish actual usage analytics from sales-demo data and CRM pipeline metrics. No aggregate from private mail or invented analytics values. |

The first implementation milestone can use local synthetic identities/provider adapters to exercise navigation, permissions, conflict and unknown outcomes. That does not authorize connecting real CRMs, creating a Team, inviting/sharing with another person, changing account-wide settings or purchasing. Root can choose the smallest actual comparison once required access and explicit mutation scope are available; this packet requests no new user handoff.
