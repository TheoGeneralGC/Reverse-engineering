# Vercel operator runbook — prepared, not executed

The selected architecture is Vercel Node24 Express plus a Turso **libSQL** HTTP
primary. Proposed project name is `rea-superhuman-tracking`. No resource,
deployment, real key or main application environment has been changed. The main
app stays unconfigured until the owned service passes actual verification.

## Account, zero-cost resource and exact identity

1. Select the intended personal Vercel account/project explicitly. Use eligible
   personal/noncommercial Hobby and Turso Free only; do not accept a paid tier,
   trial conversion, overages or upgrade. The actual integration grant/engine/
   hard-cap settings must be inspected. If Free cannot supply libSQL interactive
   write transactions, stop that setup and review the provider choice; the code
   never falls back to another engine.
2. Connect the selected Turso resource only to this project. Record project/team,
   resource/region, actual assigned stable HTTPS origin and source+lock identity.
   Keep compute and primary storage colocated; `iad1` in the prepared config is
   a proposed single region, not proof of a selected database location.
3. Set Vercel Root Directory to `apps/superhuman/collector-vercel`, enable the
   project setting for own-source imports outside Root Directory, and review
   the trace. The sole outside-root runtime module is sibling
   `../collector/src/protocol.ts`; Input/Output imports from the ancestor are
   type-only. No main API, environment file, mail database, browser profile,
   filesystem SQLite or native `.node` binary belongs in the deployment.
4. Use production's assigned exact origin in `TRACKING_PUBLIC_ORIGIN`. Do not use
   an expiring tunnel, guessed alias or a different deployment Host. No custom
   domain/DNS purchase is necessary. Preview credentials/data, if used, must be
   isolated from production. Public image ingress must not require Vercel login;
   `/v1/*` still requires this service's exact HMAC and rejects Cookie/Origin.

## One-time schema operator

Populate a separate private operator process environment through a secure path;
the package does not load an environment file. Its database URL must be the
reviewed resource, not a main application path. The operator needs schema-write
authority only for the explicit empty collector database. The following command
is a **real remote migration** when executed; it is not part of startup, health,
pixel handling, tests or deployment build:

```sh
node --experimental-strip-types --input-type=module <<'JS'
import { createClient } from '@libsql/client/web';
import { configuration } from './src/config.ts';
import { installSchema } from './src/operator.ts';
const config = configuration(process.env);
const client = createClient({
  url: config.databaseUrl, authToken: config.authToken, intMode: 'number'
});
try {
  await installSchema(client);
  console.log('collector schema installed');
} finally {
  client.close();
  for (const signer of config.signers.values()) signer.key.fill(0);
  config.cursorKey.fill(0);
}
JS
```

The operator batches own reviewed SQL inside one primary transaction, refuses a
nonempty database, checks foreign-key state on that session, verifies schema and
then commits. A failed/uncertain COMMIT is not permission to re-run installation
blindly: inspect only the selected collector schema and preserve the outcome.
Do not disable FK checks, change a marker, drop tables or adopt an unrelated
database to make setup pass. Runtime functions only validate existing schema.

## Deploy and verify the actual route

Use the reviewed repository commit and project scope. An explicitly invoked
production deployment can be prepared with `vercel deploy --prod` from this
package; do not run it until the target/access/resource are authorized and the
source is reviewed. The assigned production alias must equal the configured
origin. Strict Host validation means an arbitrary immutable deployment URL is
not interchangeable with that alias. Promotion/rollback commands are real
deployment actions. No deployment command has been run here.

For the first actual deployment, keep main tracking unconfigured and use only
owned synthetic opaque references/payloads. Use the canonical `signedHeaders`
helper from the sibling protocol, exact raw Buffer bodies and actual external
`/v1/...` targets. Keep generated keys and pixel tokens in a private fixture;
record only sanitized outcomes/hashes. Do not add a debug echo route or log a
request URL, key, token, authorization header or full upstream error.

Verify these concrete stages, once with a durable local action journal:

- Exact `/healthz` GET/HEAD returns204; it proves only marker readability.
- Signed POST `/v1/registrations` with a new synthetic operation/registration,
  account/delivery reference and token digest accepts `prepared`. Same-key GET
  `/v1/requests/:operationId` recovers that exact acceptance; current registration
  GET agrees. A prepared image does not add events.
- Explicit `armed` CAS accepts; HEAD adds no event. Two owned synthetic image
  GETs stay hidden until explicit collector `confirmed` with a synthetic opaque
  ACK. That test ACK is **not** a real mail-delivery proof.
- GET `/v1/events?accountRef=…&limit=1` and the canonical sorted cursor query yield
  two stable pages, viewer null, image-fetch evidence and no human-read claim.
  New events do not enter an earlier cursor snapshot.
- Changed body under an old signature, replayed nonce, unsorted/duplicate query,
  malformed/trailing-slash path and forged original-URL headers cannot mutate or
  redirect authority. A signed request sent to an internal `/api` spelling must
  not be accepted as `/v1`. Use only owned deployment aliases for Host mismatch
  checks; do not probe another account/domain. No header-based target recovery.
- Concurrent independent clients prove one key/CAS winner and unique sequences;
  the100-event page works on the selected remote engine within its5s transaction
  limit. Local virtual-latency controls are not a remote performance result.
- Recreate the owned function/client instance with the same database and stable
  keys. Historical receipts, nonce rejection and an already-issued cursor still
  work. A failed/unknown request must be reconciled with exact-key GET, never
  silently re-posted. Preserve all failed checks; no automatic retry of actions.

No real mail/provider/model action is required for these collector checks. Only
after this service is verified should a separate main configuration review place
the matching signer in its local0600 file and set its existing origin/file inputs.
The collector cursor key never belongs in main. Real tracked Send verification
is a separate explicitly bounded delivery action; do not infer it from synthetic
collector confirmation.

## Restore, rollback and limits

Use a consistent provider export/PITR of the selected collector database and keep
stable signer/cursor material through an access-restricted operator credential
path. Restore to a separate empty owned resource before relying on it; verify
old receipt, nonce replay, event/cursor and registration binding. Do not run the
Render filesystem backup helper or treat a function `/tmp` file as durable data.
A code rollback retains remote state, so schema and key compatibility must be
checked. These managed backup/restore operations remain unexecuted.

Free limits can make the collector unavailable. Keep upgrades/overages disabled
and inspect the selected account's hard-stop behavior; never turn on billing
implicitly. Public GIF uniformity can mask a write failure and therefore cannot
prove an email was unopened. Vercel necessarily receives pixel requests and may
retain paths in platform logs; actual account retention is an operational fact
to inspect, not a promise of no provider logging. This application emits no
token/URL credential log and does not identify named recipients or human reads.
